Static Character Runtime
后续开发路线与阶段验收标准
版本：V0.1 后续工作规划
日期：2026-11-01

============================================================
0. 文档目的与当前项目状态
============================================================

本文件用于确认 Static Character Runtime（通用静态角色表现系统）接下来的开发顺序、每一步的实施方法、目标、交付物和验收标准。

当前已知进度：
- 已完成初步动作控制面板。
- GitHub 娘状态图片素材已准备并命名，已打包上传。
- 项目目标是建立可复用的通用角色表现系统，而不是只制作 GitHub 娘展示网页。
- 第一阶段使用完整静态图片代表动作，通过状态切换呈现角色表现。
- 后续由 AI 根据对话和事件自动选择动作。
- 当前先验证静态图片加载、动作切换和状态管理，不急于接入 AI。

核心原则：
1. 角色素材、状态管理、AI 决策、渲染展示相互分离。
2. GitHub 娘是第一个示例角色，不是系统唯一支持的角色。
3. 新增角色和动作尽量通过资源目录与配置文件完成，不应要求修改核心代码。
4. 所有 AI 输出都必须经过程序校验，不能让 AI 直接操作图片路径或任意修改界面。
5. 先完成稳定、可测试的基础系统，再增加智能化和复杂功能。
6. 每一阶段必须有可检查的交付物和明确验收标准；未通过验收，不进入下一阶段。

============================================================

建议按以下顺序推进：

A. 盘点并稳定现有原型
B. 建立角色资源配置与加载规范
C. 完善状态管理器

F. 接入 AI 动作决策

H. 实现角色包导入与多角色验证
I. 整理发布版本与后续平台适配

每个阶段单独完成、测试并建立版本记录。每次改动前先阅读现有项目，不要假定项目结构与本文示例完全一致。优先小步修改，保留现有可用代码。涉及大规模重构时，先说明原因、影响范围和回滚方案，再等待用户确认。

弄清楚动作控制面板已经完成到什么程度，确认代码可运行、结构可理解，并建立可靠的开发起点。

实施步骤：

2. 找到应用入口、动作控制面板、图片展示区域和状态切换逻辑。
3. 记录已实现功能，不重复开发。
4. 检查是否使用临时图片、硬编码图片路径或写死的动作列表。
5. 在本地启动项目，记录启动命令和运行方式。
6. 检查浏览器控制台和终端错误。
7. 建立一次 Git 提交或备份，标记为“现有动作控制面板基线”。

交付物：
- 当前项目结构说明。
- 已实现功能清单。
- 项目启动方法。
- 已知问题清单。
- 可回滚的基线版本。

验收标准：
- 项目可按文档步骤启动。
- 已完成的动作控制面板仍然可用。
- 能明确指出图片展示和状态切换分别由哪些模块负责。
- 不存在未解释的启动错误。
- 有办法恢复到本阶段开始时的状态。

本阶段暂不接入 AI API，也不重写整个项目。

3. 阶段 B：建立角色资源配置与加载规范
============================================================

目标：
让系统通过角色配置文件加载图片，而不是把图片路径和角色信息写死在界面代码中。

建议资源结构（应按实际项目调整）：

characters/
  github_girl/
    character.json
    assets/
      idle.png
      thinking.png
      talking.png
      listening.png
      working.png
      happy.png
      surprised.png
      confused.png
      sad.png
      angry.png
      waving.png
      celebrating.png

配置文件建议包含：
- 角色唯一 ID、显示名称和版本。
- 画布宽度和高度。
- 默认状态 ID。
- 状态列表。
- 每个状态对应的图片相对路径。
- 状态说明。
- 可选的默认展示位置或缩放参数。

实施步骤：
1. 盘点 ZIP 解压后实际存在的文件名，不猜测文件名。
2. 将实际图片与状态 ID 建立映射。
3. 检查图片格式、尺寸、透明通道和文件大小。
4. 对不存在的状态标记为缺失，不要指向不存在的图片。
5. 创建或完善 character.json。
6. 编写资源加载模块，读取配置并验证必需字段。
7. 图片路径使用相对角色目录的安全路径；拒绝路径穿越等异常路径。
8. 图片加载失败时显示明确错误，并回退到默认状态；默认图也失败时显示占位提示。

交付物：
- GitHub 娘角色目录。
- 经过验证的 character.json。
- 资源加载模块。
- 资源检查结果或报告。

验收标准：
- 系统能从配置文件读取角色名称和状态列表。
- 不修改核心代码即可调整状态对应图片。
- 缺少图片时有可理解的错误提示。
- 至少成功加载 5 个真实状态图片。
- 默认状态正确显示。

注意：
- 不假设图片已经透明或统一尺寸，必须实际检查。
- 若图片画布尺寸不同，先报告差异，再决定是否批量处理。
- 保留原始素材，不覆盖用户唯一的原图。

4. 阶段 C：完善状态管理器
============================================================

目标：
从“按钮点击就切换图片”升级为可被程序和 AI 调用的稳定状态系统。

区分三种概念：

1. 基础状态（Base State）：角色当前长期处于的工作阶段，例如 idle、listening、thinking、talking。
2. 临时覆盖状态（Override State）：短时间表现的动作或情绪，例如 waving、celebrating、surprised、apologizing。
3. 当前显示状态（Effective State）：由基础状态和临时覆盖状态综合计算出的最终图片状态。

建议初始优先级：
- 系统错误/安全提示：100
- 特殊交互动作：80
- 情绪表现：60
- 工作阶段：40
- 默认待机：10

优先级为初始建议，应通过实际体验调整。

实施步骤：
1. 定义状态数据结构。
2. 定义设置基础状态的方法。
3. 定义添加临时覆盖状态的方法。
4. 定义清除或结束临时状态的方法。
5. 定义优先级比较规则。
6. 定义持续时间和自动结束机制。
7. 定义动作结束后恢复到哪个基础状态。
8. 定义同优先级冲突时的处理方式。
9. 定义未知状态的回退策略。
10. 将控制面板改为调用状态管理器，而不是直接修改图片元素。

建议接口（概念示例）：
- setBaseState(stateId)
- pushOverride(stateId, priority, duration)
- clearOverride(overrideId)
- getEffectiveState()
- resetToDefault()

验收标准：
- 按钮和程序事件使用同一套状态接口。
- 临时动作结束后恢复到正确的基础状态。
- 低优先级事件不能覆盖仍有效的高优先级动作。
- 未知状态不会导致程序崩溃。
- 连续触发多个动作时不会出现状态永久卡死。
- 可通过测试用例复现并验证状态优先级。

重要提醒：
不要只设计一个“当前状态字符串”。如果没有基础状态与临时覆盖状态的区分，容易出现庆祝动作结束后错误回到 idle，而不是继续 talking 的问题。

5. 阶段 D：实现可靠的图片切换与视觉过渡
============================================================

目标：
让状态切换稳定、清晰，不出现闪烁、空白、比例跳动或位置突变。

实施步骤：
1. 统一角色展示区域的宽高和定位规则。
2. 以固定画布区域显示图片，使用 contain 等不裁切策略。
3. 切换前预加载下一张图片。
4. 图片加载成功后再执行切换。
5. 使用短暂淡入淡出作为第一种过渡效果。
6. 过渡期间避免多个切换请求互相打断造成闪烁。
7. 图片加载失败时保留上一张有效图片或回退默认图。
8. 检查不同状态图片的角色大小、视觉中心和脚底/身体锚点是否一致。
9. 若素材本身存在明显位置偏差，先形成问题清单，再决定是否处理原图。

建议：
- 初始淡入淡出时长可设为 150–250ms，之后通过体验调整。
- 第一版不需要复杂弹跳、旋转或持续呼吸动画。
- 视觉过渡只负责展示，不应改变状态管理规则。

验收标准：
- 连续切换图片时没有明显白屏或闪烁。
- 图片加载失败不会使展示区域崩溃。
- 不同状态间不会发生明显的非预期缩放。
- 可在控制面板中快速连续切换并保持稳定。

6. 阶段 E：建立统一事件接口
============================================================

目标：
让系统不再只响应控制面板按钮，还能接收外部程序、聊天系统或 AI 助手发送的事件。

建议事件类型：
- user_message_received
- user_input_started
- assistant_thinking
- assistant_response_started
- assistant_response_chunk
- assistant_response_finished
- task_started
- task_progress
- task_succeeded
- task_failed
- greeting
- farewell

实施步骤：
1. 定义事件数据格式。
2. 定义事件分发入口。
3. 将控制面板按钮改为发送测试事件。
4. 将事件转换为基础状态或临时覆盖状态。
5. 为未知事件提供忽略和日志记录机制。
6. 确保事件接口不依赖某个特定大模型。

概念示例：
{
  "type": "assistant_thinking",
  "timestamp": "2026-11-01T12:00:00+08:00",
  "payload": {}
}

验收标准：
- 外部模块可通过统一入口发送事件。
- 同一种事件在相同配置下产生一致的状态结果。
- 事件接口与图片渲染模块相互独立。
- 可用模拟事件测试，不需要真实 AI。

7. 阶段 F：接入 AI 动作决策
============================================================

目标：
让 AI 根据对话语境和事件提出动作意图，再由程序验证和执行。

原则：
AI 只提出动作建议；状态管理器负责最终决定；渲染器只负责展示。

实施步骤：
1. 明确 AI 可以使用的状态白名单。
2. 向 AI 提供当前角色状态清单及简短描述。
3. 设计结构化输出格式。
4. 对 AI 输出进行 JSON/schema 校验。
5. 检查 state 是否在角色已注册状态中。
6. 检查 duration 和 intensity 是否在允许范围。
7. 对非法或不完整输出使用安全默认值。
8. 将合法动作意图交给状态管理器。
9. 加入动作冷却时间或重复动作抑制，避免频繁切换。
10. 保留手动控制覆盖 AI 的能力。

建议输出格式：
{
  "state": "happy",
  "emotion": "happy",
  "intensity": 0.7,
  "duration_ms": 2500,
  "reason": "用户分享了一个积极进展"
}

注意：
- 不允许 AI 输出任意本地文件路径。
- 不允许 AI 创建未注册动作。
- 不要让每个文本 token 都触发一次图片切换。
- 优先在消息阶段或明确事件节点触发决策。
- API 密钥使用环境变量或安全配置，不写入前端公开代码或提交到 Git。
- ChatGPT Plus 订阅不等于 API 额度，云端 API 可能产生额外费用。

验收标准：
- AI 能从现有动作白名单中选择状态。
- 非法输出不会破坏程序。
- 对简单测试对话，动作选择基本符合预期。
- 连续文本输出不会导致角色疯狂切图。
- 关闭 AI 后，手动控制和模拟事件仍正常。

8. 阶段 G：调试、日志与异常处理
============================================================

目标：
让用户知道角色为什么切换状态，并快速定位问题。

建议调试面板显示：
- 当前基础状态。
- 当前临时覆盖状态。
- 最终显示状态。
- 最近一次事件。
- 最近一次 AI 动作建议。
- AI 输出是否通过校验。
- 动作优先级。
- 剩余持续时间。
- 最近若干条状态切换记录。
- 资源加载错误。

实施步骤：
1. 建立统一日志格式。
2. 记录事件接收、状态决策、资源加载和渲染结果。
3. 在开发模式显示调试面板。
4. 提供清空日志和复制日志功能。
5. 对用户可见错误给出可理解的提示。
6. 不记录不必要的敏感对话内容或 API 密钥。

验收标准：
- 能解释最近一次状态变化的原因。
- 能定位图片缺失、状态无效和 AI 输出异常。
- 生产展示界面可以隐藏调试面板。
- 日志不泄露密钥。

============================================================

目标：
证明系统是通用的，而不是只为 GitHub 娘写死的展示页面。

- GitHub 娘不再是核心代码中的特殊分支。

11. 每一阶段的通用工作流程
============================================================

每次让 Codex 或其他编程助手执行任务时，使用以下流程：

第一步：先检查
- 阅读相关代码和文件。
- 说明当前实现。
- 找出与本阶段目标有关的问题。
- 不要先修改文件。

第二步：给出方案
- 列出准备修改的文件。
- 说明每个文件要改什么。
- 说明是否需要安装新依赖。
- 说明可能影响的已有功能。

第三步：小步实施
- 一次只完成一个可验证的小目标。
- 不顺便重构无关模块。
- 保留现有功能。
- 不覆盖原始角色素材。

第四步：运行验证
- 执行项目构建或测试。
- 手动检查关键交互。
- 检查浏览器控制台和终端。
- 如无法实际验证，明确说明未验证部分。

第五步：总结交付
- 完成了什么。
- 修改了哪些文件。
- 如何运行。
- 如何测试。
- 尚存问题。
- 下一步建议。

第六步：用户验收
- 用户确认达到目标后，才进入下一阶段。
- 重要阶段建立 Git 提交或备份。

14. 项目成功的定义
============================================================

V0.1 的成功，不是拥有很多动作，也不是界面多么华丽，而是满足以下条件：

1. 能够加载一套角色资源。
2. 能够读取角色配置。
3. 能够通过统一状态接口切换图片。
4. 状态切换可靠，不会轻易卡死或闪烁。
5. 能够处理缺失图片和非法状态。
6. 能够通过模拟事件驱动角色。
7. 核心系统不依赖 GitHub 娘的专属代码。

达到这些条件，就说明第一版通用静态角色表现系统已经成立。之后再接入 AI，才是在稳定底座上增加智能，而不是让 AI 掩盖基础系统的问题。

============================================================
结语
============================================================

本项目不是要用静态图片完全取代 Live2D，而是探索一种制作成本更低、素材要求更简单、易于被不同 AI 助手调用的角色表现方式。

先做出稳定、可扩展的基础系统，再逐步增加 AI 决策、更多角色和其他渲染方式。

GitHub 娘是第一个角色。
Static Character Runtime 是真正要建设的系统。

开发节奏：先验证，再抽象；先完成，再扩展；每一步都留下可检查的成果。
